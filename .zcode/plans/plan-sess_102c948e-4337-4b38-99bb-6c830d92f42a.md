# 章节超长守卫修复计划（feature/chapter-over-length-guard）

## 根因回顾
写作链路只有"低于下限自动续写"，超过上限（hardMax = 目标×1.25，契约已定义）无任何收束；验收层对超长无确定性判定，而修复环 `getRepairModeHint` 早已预留 `LENGTH_OVER_HARD_MAX` → 整章压缩的入口——但全库无生产者，功能闭环断在中间。minimax-m3 顶满 maxTokens=6000 的输出（约 8000-10000 字）因此畅通无阻地入库并通过验收。

## 修复设计（两层 + Prompt v9）

### Layer A：写作图超长守卫（根因修复）
`server/src/services/novel/chapterWritingGraph.ts`
- 把 `enforceTargetLength` 扩展为区间守卫：先"超 hardMax 压缩"，再"低于 softMin 续写"（现有续写逻辑原样保留复用）。
- 新增 `condenseOverLength`：调用 `runTextPrompt`，`mode: "condense"`、`stage: "writer_condense"`、`triggerReason: "length_condense"`、`maxTokens: 6000`、`temperature: 0.8`（对齐 writer_extend 惯例）；上下文块传入完整草稿 + 当前字数/目标/硬上限。
- 接受规则（有界、不丢内容）：压缩结果非空且严格变短才接受；接受后若仍低于 softMin，走现有续写兜底；压缩失败/为空则保留原稿放行（交给 Layer B）。单章最多 1 次压缩调用，无循环。

### Layer B：验收确定性超长判定（闭环补全）
`server/src/services/novel/runtime/ChapterAcceptanceAssessmentService.ts` 的 `normalizeAssessment`
- 确定性检查（属允许的"确定性后处理/安全护栏"）：实际字数 > hardMax 时，强制在最前注入 blockingIssue `{code: "LENGTH_OVER_HARD_MAX", severity: medium, category: mode_fit}` 和 repairDirective `{mode: patch, target: plot, instruction: 含"超出"措辞的整章压缩指令}`（置于队首以存活 slice(0,5)/slice(0,4)；指令措辞含 OVER 标记词，保证修复成功后二次验收能被既有 reconcile 逻辑正确豁免）。
- 效果：注入 code → AuditIssue → `runtimePackage.audit.openIssues` → `getRepairModeHint` 命中 `compress_chapter_for_length` → 既有 patch 修复环执行压缩；修复后仍超长则按既有 defer_and_continue 记质量债，不阻塞全书（符合 AGENTS 非阻塞规则）。
- 阈值只用 hardMax（softMax~hardMax 之间维持 Prompt 软约束，不升级为修复项）。

### Prompt v9：writer 增加 condense 模式
`server/src/prompting/prompts/novel/chapterWriter.prompts.ts` + `server/src/prompting/registry/promptAssetLoaderEntries.ts`
- `version: "v8" → "v9"`（两处同步，registry key 为 `novel.chapter.writer@v9`；officialTemplates 版本动态引用无需改）。
- `mode` 联合类型加 `"condense"`；render 增加：系统侧【压缩要求】（只删减收束、不新增情节、必须保留 mustAdvance/义务兑现/结尾钩子、优先删除重复复读/碎片对话/无信息量描写、输出完整正文不出说明）；Human 侧任务模式文案。draft/continue 分支完全不动。
- 无 shared schema 变更（`resolveLengthBudgetContract` 已返回 hardMax，直接消费）。

## 测试（node --test，编译 dist 风格）
- 新增 `server/tests/chapterOverLengthGuard.test.js`：区间内不触发压缩；超 hardMax 触发恰好一次压缩且保存压缩稿；压缩返回空保留原稿。用 `setPromptRunnerLLMFactoryForTests` 注入假 LLM，deps 手搓（参照 chapterPatchRepair.test.js / chapterRuntimeBoundary.test.js 既有风格）。
- 扩展 `server/tests/chapterAcceptanceAssessmentService.test.js`：超 hardMax 注入 issue+directive 且 status=repairable；区间内行为不变；softMax~hardMax 之间不注入。

## 流程
- 从 `beta` 拉 `feature/chapter-over-length-guard` 开发，完成后按阶段提交
- 提交前按 readme-release-updater 更新 release-notes + README（用户视角：单章超过硬性篇幅上限时自动压缩收束，防止个别模型把章节写到八千字以上）
- Wiki：`docs/wiki/workflows/` 新增章节字数控制链条目（draft 软区间 → 低于下限续写 → 超硬上限压缩 → 验收确定性 LENGTH_OVER_HARD_MAX → patch 压缩修复 → 质量债），并记录"修复环已预留 compress hint 但上游无生产者"这一断链教训

## 明确不做（non-goals）
- 不回填改写已生成的 112-141 章正文（覆盖已批准内容需你单独授权；可从界面按章重写，新验收环重跑时也会给压缩指令）
- 不改 maxTokens=6000、不动模型路由配置（那是配置层面的选择）
- 不改 shared 契约结构

## 风险
- 超长章节多一次 LLM 调用成本（仅超 hardMax 时触发，可接受）
- 弱服从模型压缩后仍可能超限 → Layer B + 既有修复环兜底，最终落质量债，不阻塞全书链路
